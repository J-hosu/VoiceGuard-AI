# 탐지 모델 학습 기록

보이스피싱 분류기(빠른 경로)를 어떤 데이터로, 어떻게 학습했고, 결과가 어땠는지 남기는 기록이다.
새로 학습할 때마다 아래에 항목을 추가한다.

- 분류기의 역할: 통화 전사문을 보고 사기 확률(0~1)을 낸다. 실시간 화면의 위험도는 이 점수 30%와
  Claude 상태 추적기 점수 70%를 합친 값이다(`docs/API_SPEC_V2.md` 4.2절).
- 학습·평가는 모두 H100 서버(`~/voiceguard`)에서 했다. 데이터(`data/`)와 모델(`models/`)은 git에 올리지 않는다.

## 2026-11-15 · 피싱용 위조 문서 점검 (학습 없이 평가 세트로 검증)

문서 사진 한 장을 보고 피싱에 쓰이는 위조 문서의 특징이 있는지 판별하는 기능이다(`POST /analyze/document`,
앱 '문서 점검' 화면). 모델을 새로 학습하지 않는다. Claude가 이미지를 읽고, 프롬프트에 넣은 판단 기준으로
위험도를 낸다. 대신 정확도를 잴 평가 세트를 직접 만들었다.

### 한눈에 보기

| 항목 | 내용 |
| --- | --- |
| 판정 | Claude Opus 5.5 이미지 판독 (effort low), `services/document_analyzer.py` |
| 평가 세트 | 원본 46장 (위조 31 / 정상 15) + 정상 문서의 저화질 변형 15장. dev 23장 / test 23장 |
| 결과 (test, 기준 0.7) | 정확도 95.7%. 위조 15장 중 14장 탐지, 정상 8장 오경보 0, 저화질 정상 변형 8장 오경보 0 |
| 평가 명령 | `SPLIT=dev` 또는 `SPLIT=test python -m backend.app.eval_documents` (Claude API 비용 발생, 1회 약 30장) |

### 공개 데이터 조사

- 이 과제(사기범이 처음부터 만든 가짜 공문 대 진짜 문서)에 맞는 공개 데이터셋은 한국어에도 외국어에도 없었다.
- AI Hub: '위조', '위변조' 검색 결과는 얼굴 위조 방지와 필체 모사 데이터뿐이다. 공공행정문서 OCR(약 90만 장)은
  정상 문서만 있어 정상 표본으로만 쓸 수 있고, 신청·승인이 필요하다.
- 공공데이터포털: 보이스피싱 통계, 영상, 설문만 있고 문서 이미지는 없다.
- 해외 문서 위조 데이터(DocTamper, Find it again!, RTM, T-SROIE, AIForge-Doc 등)는 진짜 영수증·문서 안의
  글자 일부를 고친 픽셀 단위 변조를 다룬다. 처음부터 만든 가짜 공문은 픽셀이 깨끗할 수 있어 다른 문제다.
  SIDTD와 MIDV-2020은 유럽 모의 신분증이다.
- 그래서 경찰청, 금융감독원, 검찰, 언론이 "사기범이 만든 문서"라고 밝혀 공개한 이미지와, 발급 기관이 공개한
  실제 문서·법정 서식을 하나씩 모아 라벨을 붙였다.

### 평가 세트 구성

- 위조 31장: 경찰청 전기통신금융사기 통합대응단, 금융감독원, 서울중앙지검의 보도자료와 언론 기사 사진이다.
  가짜 검찰·법원·금감원 공문, 구속영장, 검사 공무원증, 대출약정서, 지급정지요청서, 관공서·군부대를 사칭한
  노쇼 사기 공문, 기관 사칭 이메일 등이 있다. 출처가 붙인 '가짜' 배지나 문구는 잘라냈다.
- 정상 15장: 법제처 법정 서식(출석요구서, 수사결과 통지서, 영장청구서, 과태료·세금 고지서), 금감원의 실제
  공시송달 문서, 국세청·국민건강보험공단·우정사업본부가 공개한 견본, 은행 상품설명서다.
- 라벨마다 수집 에이전트와 별도의 검증 에이전트가 출처 페이지를 다시 열어 확인했다. 중복 7장과, 판독이 안 되거나
  출처가 가린 개인정보가 드러나는 원본 등 10장을 뺐다. 출처 페이지에 'AI 학습 및 활용 금지'가 적힌 3장도 뺐다.
- sha256 기준으로 dev(프롬프트 조정용)와 test(최종 보고용)로 나눴다. test는 조정에 쓰지 않았다.
- 정상 문서 대부분이 깨끗한 PDF 렌더라서, 화질만 보고 위조라고 하는지 확인해야 했다. 그래서 정상 문서마다
  메신저로 받은 사진처럼 바꾼 변형(축소, 살짝 회전, 흐림, 잡음, JPEG 압축)을 만들어 따로 쟀다.
- 이미지는 `data/eval_documents/`(git 제외)에, 출처 목록은 `backend/eval/documents_manifest.json`에 있다.

### 결과 (기준 0.7 = 앱의 '주의' 기준)

| 평가 | 수정 전 프롬프트 | 수정 후 프롬프트 |
| --- | --- | --- |
| dev 원본 23장 (위조 16 / 정상 7) | 정확도 82.6%, 위조 12/16 탐지, 오경보 0/7 | 정확도 95.7%, 위조 15/16 탐지, 오경보 0/7 |
| dev 저화질 정상 변형 7장 | 오경보 0/7 | 오경보 0/7 |
| test 원본 23장 (위조 15 / 정상 8) | 정확도 95.7%, 위조 14/15 탐지, 오경보 0/8 | 정확도 95.7%, 위조 14/15 탐지, 오경보 0/8 (2회 실행, 판정 같음) |
| test 저화질 정상 변형 8장 | 오경보 0/8 | 오경보 0/8 |

- 무엇을 고쳤나: dev에서 놓친 위조 4장 중 3장은 위험 신호를 찾고도 0.55~0.60을 줬다. 신호는 개인 휴대전화와
  포털 이메일만 적힌 금융회사 직원 명함, 개인에게 이메일로 자료 제출을 요구하는 금감원 사칭 메일, 업체에 물품
  구매를 알리는 구청 명의 공문이었다. 그래서 신호별 점수 구간을 프롬프트에 넣었다(신호를 찾았으면 그 구간
  점수를 준다). "화질이 낮다는 이유만으로 점수를 올리지 않는다"는 규칙과, 노쇼 사기 신호(`vendor_order`)도 넣었다.
- test는 수정 전에도 95.7%였고, 수정 후에도 판정이 같았다. 이번 수정은 dev의 경계 사례를 바로잡았고 test에서
  나빠진 것은 없다. 정상 문서 점수는 최대 0.10에서 0.15로 조금 올랐다(기준 0.7과는 거리가 멀다).
- 수정 전후 모두 놓친 위조 2장: 은행 대출약정서 양식을 그대로 베끼고 요구 문구가 없는 문서(fss_04), 회사를
  상대로 한 감독 업무 요청처럼 쓴 금감원 명의 자료제출 요구서(police_10). 문서만 봐서는 진짜와 구별할 근거가
  없는 경우다. 사용자가 "어떻게 받았는지"를 함께 적으면 나아질 수 있다(평가에서는 설명 없이 이미지만 넣었다).

### 한계

- 표본이 작다. test 위조 탐지 14/15의 95% 신뢰구간은 약 70~99%, 오경보 0/8의 신뢰구간은 0~32%다.
- 정상 문서가 대부분 빈 서식이라 맞히기 쉬운 편이다. 내용이 채워진 실제 공문, 영장, 대출 승인서는 공개된 것이
  거의 없다. 저화질 변형으로 화질 편향은 확인했지만, 내용 편향은 남아 있다.
- 위조 이미지는 모두 기관과 언론이 공개한 사례라 모델이 학습 중에 봤을 수 있다. 새 수법의 가짜 문서에서는
  성능이 더 낮을 수 있다.
- 같은 사기 조직이 쓴 검찰 공문 틀 9장이 dev와 test에 나뉘어 있다. 프롬프트에 넣은 신호(사칭 이메일, 노쇼
  공문)와 같은 유형이 test에도 1장씩 있다. 그래서 test 결과가 완전히 독립적인 검증은 아니다.
- 출처별 이용 조건(공공누리 유형 등)을 항목마다 확인하지는 않았다. 그래서 이미지는 저장소에 올리지 않는다.

## 2026-11-15 · 스미싱 문자 분류기 (sms_roberta)

통화가 아니라 **문자·메신저 메시지** 한 통을 보고 스미싱인지 판별하는 분류기다. 문자 검사 기능
(`POST /analyze/message`, 앱 '문자 검사' 화면)에서 Claude 판단과 함께 쓴다.

### 한눈에 보기

| 항목 | 내용 |
| --- | --- |
| 모델 | KLUE-RoBERTa (`klue/roberta-base`) |
| 저장 위치 | 서버 `models/sms_roberta` |
| 학습 데이터 | `data/SmishingSMS.json`, 문자 17,547건 (스미싱 5,649 / 정상 11,898) |
| 원본 | Hugging Face `jmjmjm3/kor-smishing-message` (`smishing.csv`, 18,270행, CC BY-NC-SA 4.0 — **비상업 조건**) |
| 학습 시간 | 약 1분 (H100, fp16) |
| 실제 판정 | 분류기 점수 40% + Claude 판단 60% (`services/message_analyzer.py`) |

### 데이터 구성

- 원본에서 라벨이 `정상`/`스미싱`인 행만 쓰고, 4자 미만 문자와 본문이 똑같은 중복을 합쳐 723건을 뺐다.
- 같은 틀에 숫자·링크만 바뀐 스미싱 문자가 많다. 숫자와 링크를 가린 본문으로 묶음(group)을 만들어
  (13,964개) 해시 분할(`SPLIT=hash`)을 했다. 같은 틀의 문자가 학습과 평가에 나뉘어 들어가 점수가
  부풀려지는 것을 막기 위해서다. 코드: `backend/app/build_sms_dataset.py`
- 통화 분류기와 같은 학습 스크립트(`train_transformer.py`)를 그대로 쓴다(문자 한 통 = 발화 1개짜리 통화).
  앞부분 증강과 문장부호 정규화는 쓰지 않았다(문자는 짧고, 문장부호·링크 모양 자체가 신호다).

### 결과

| 평가 | 분류기 단독 | Claude 단독 | 융합(실제 판정) |
| --- | --- | --- | --- |
| 학습에 쓰지 않은 묶음 3,600건 (스미싱 1,283) | 정확도 99.44%, 정밀도 99.30%, 재현율 99.14%, F1 99.22% | - | - |
| 위 평가셋에서 뽑은 80건 (스미싱 40 / 정상 40) | 80/80 | 78/80 | 80/80 |
| 따로 쓴 문자 16건 (`backend/eval/messages.json`) | 16/16 | 15/16 | 16/16 |

따로 쓴 16건은 데이터와 문체가 다른 최신 수법(과태료·건강보험 환급·부고·자녀 사칭)과, 사기처럼
보이지만 정상인 문자(은행의 사칭 주의 안내, 국세청 신고 안내, 카드 승인 알림, 인증번호)를 섞었다.
평가 명령: `python -m backend.app.eval_messages` (Claude API 비용 발생).

### 한계

- 원본 라벨은 데이터 제공자가 붙인 것이고 설명 열은 LLM이 쓴 것으로 보여, 라벨 오류가 일부 있을 수 있다.
- 데이터의 정상 문자는 일상 대화가 많아 "정상 기관 안내 문자"가 적다. 따로 쓴 16건은 우리가 직접 쓴
  것이라 소수이고 편향이 있을 수 있다.
- 원본이 비상업 라이선스(CC BY-NC-SA 4.0)라, 상용화할 때는 데이터를 바꾸거나 허락을 받아야 한다.
- 링크는 접속하지 않고 모양만 점검한다(단축 주소, IP 주소, 사기에 자주 쓰이는 최상위 도메인, 기관명을
  넣어 꾸민 주소). 실제 악성 여부는 확인하지 않는다.

## 2026-11-15 · v2 (현재 서버에 적용된 모델)

### 한눈에 보기

| 항목 | 내용 |
| --- | --- |
| 적용 모델 | KLUE-RoBERTa (`klue/roberta-base`), 한국어 사전학습 모델 |
| 저장 위치 | 서버 `models/koelectra` (폴더 이름은 예전 그대로, 내용은 RoBERTa) |
| 이전 모델 백업 | 서버 `models/koelectra_v1_backup` (KoELECTRA v1) |
| 학습 데이터 | `data/PhishCatch-Data-v2.json`, 통화 4,091건 (사기 1,374 / 정상 2,717) |
| 학습 시간 | 약 95초 (H100, fp16) |

### 왜 다시 학습했나 (v1의 문제)

v1(KoELECTRA)은 학습 때 평가로는 정확도 99%였지만, 그 평가는 학습 데이터와 같은 종류의 통화만 봤다.
다른 종류의 통화로 재 보니 두 가지 문제가 있었다.

1. **모르는 유형을 못 잡는다.** 사기 데이터가 금감원 공개 녹취(기관 사칭, 대출 사기) 두 유형뿐이라
   납치 협박·지인 사칭·카드배송 사칭 대본에는 0~6%의 점수를 줬다.
2. **주제만 보고 사기로 본다.** 피싱 피해를 상담하는 정상 통화(KISA 118)의 약 60%에서 통화 중 한 번은
   주의 기준(0.70)을 넘었다.

중간 실험에서 배운 것: 정상 데이터만 늘리거나 통화 앞부분 증강만 넣으면 오히려 나빠진다. 사기 데이터가
한 출처(금감원 녹취 전사)뿐이면 모델이 내용이 아니라 "그 출처의 전사 말투"를 사기로 외운다. 사기 쪽
데이터의 유형과 출처를 함께 넓혀야 한다. (후보 `koelectra_prefix`, `koelectra_v2a`는 그래서 쓰지 않았다.)

### 공식 사례 기반 생성 방법

- **근거 자료**: 금융감독원 「보이스피싱 피해사례」 72건, 「소비자경보」 40건, 경찰청 통합대응단
  「피싱 예·경보」 2건, 「피싱 시나리오」 7건. 본문을 쓸 수 있는 121건만 썼다(경찰청 예·경보는 대부분
  이미지라 제외됨). 수집 결과는 서버 `data/official/cases.json`.
- **생성**: 사례 설명을 그대로 주고, 그 수법이 실제 통화에서 어떻게 들릴지를 Claude(Opus 5.5, Batch API)로
  전사본 형태로 만들었다. 사례 하나당 사기 통화 4개(끝까지 속는 통화, 의심하는 통화, 초중반에 끊기는 통화,
  확인하겠다는 것을 막는 통화)와 정상 쌍둥이 통화 3개.
- **정상 쌍둥이 통화를 넣은 이유**: 같은 주제(카드 배송, 대출 안내, 가족의 돈 부탁)가 정상적으로 일어나는
  통화를 함께 넣어야 모델이 "주제어 = 사기"로 배우지 않는다.
- **사용량**: 요청 288건, 입력 약 85만 토큰, 출력 약 77만 토큰.
- 코드: `backend/app/generate_official_scenarios.py`

"탐지"와 "경보"는 점수가 주의 기준 0.70 이상인 경우다. KLUE-RoBERTa를 고른 이유는 통화 전체 탐지율과
별도 대본 탐지가 가장 좋고 점수 출렁임이 가장 적어서다. KcELECTRA는 초반 탐지가 조금 빠르지만 정상 통화
오경보가 더 많았다.

### 교체 후 확인

- 전체 시스템 회귀 평가(`python -m backend.app.eval_loop`, 분류기 + Claude 추적기 + 대응 에이전트): 12/12 통과
- 금감원 실제 녹취를 실시간 경로로 흘려보낸 시험
  - 검찰 사칭: 주의 20초, 강한 경고 29초 (v1: 21초, 37초)
  - 대출 사기: 주의 26초, 강한 경고 45초 (v1: 34초, 43초)
  - 정상 은행 상담(합성 음성): 끝까지 1~7%, 경고 없음

### 한계

- 새 유형(지인 사칭, 카드배송, 기타)의 평가 통화도 Claude가 생성한 것이다. 학습에 쓰지 않은 사례에서
  만든 통화로 평가했지만 실제 통화보다 쉬울 수 있다. 실제 녹취로 확인한 것은 기관 사칭과 대출 사기뿐이다.
- 납치 협박은 공식 사례가 4건뿐이라 평가셋에 들어가지 않았다. 별도 대본 1개로만 확인했다.
- 사기와 주제가 같은 정상 통화에서 분류기 단독 점수가 통화 중 한 번이라도 기준을 넘는 비율이 24~43%다.
  화면의 위험도는 추적기 점수와 합쳐지므로 회귀 평가에서는 오경보가 없었다.
- 실제 전화 음질의 정상 통화로는 평가하지 못했다(공개된 정상 통화 녹취가 없음).

### 공식 사례 검색(RAG)을 탐지에 쓰지 않은 이유

금감원·경찰청 사례 121건을 검색 자료로 넣어 "지금 통화와 비슷한 공식 사례"를 찾는 실험을 했다(글자 n-gram TF-IDF).

| 색인 방식 | 결과 |
| --- | --- |
| 사례 설명문을 색인 | 생성 통화 668건의 원 사례를 1순위로 찾은 비율 37.9%, 3순위 안 57.3%, 유형 일치 65.0% |
| 사례에서 생성한 통화를 색인 (같은 사례는 빼고 평가) | 유형 일치 79.9% |

유형을 맞히는 정확도가 80% 수준이고 정상 통화와 사기 통화의 유사도 범위가 겹쳐서(0.14~0.24 대 0.23~0.40)
탐지 점수에 넣으면 오히려 흔들릴 수 있다. 그래서 탐지에는 쓰지 않고, 위험으로 판정된 통화의 신고용 요약과
수사 지원 화면에 출처 링크가 달린 "유사 공식 사례"로만 붙인다. 이때 유형은 Claude 추적기가 정한 것을 우선한다.
코드: `backend/app/services/official_cases.py`
