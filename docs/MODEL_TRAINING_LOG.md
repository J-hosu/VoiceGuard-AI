# 탐지 모델 학습 기록

보이스피싱 분류기(빠른 경로)를 어떤 데이터로, 어떻게 학습했고, 결과가 어땠는지 남기는 기록이다.
새로 학습할 때마다 아래에 항목을 추가한다.

- 분류기의 역할: 통화 전사문을 보고 사기 확률(0~1)을 낸다. 실시간 화면의 위험도는 이 점수 30%와
  Claude 상태 추적기 점수 70%를 합친 값이다(`docs/API_SPEC_V2.md` 4.2절).
- 학습·평가는 모두 H100 서버(`~/voiceguard`)에서 했다. 데이터(`data/`)와 모델(`models/`)은 git에 올리지 않는다.

## 2026-11-16 · 통화 분류기 v5 (가린 개인정보 자리를 가짜 값으로 채움) — 서비스에 올림

공개 데이터는 개인정보를 가려서 배포한다. v3c 학습 데이터의 가림은 출처마다 달랐다.

| 출처 | 라벨 | 가린 방식 |
| --- | --- | --- |
| AI Hub 금융·민원 상담 3,901건 | 정상 | 원본은 ●, ★, OO, ㅇㅇ 같은 기호로 가렸다. 변환기가 이 기호를 지워, 87%(3,392건)의 통화에서 54,402곳이 비었다('저는 입니다'). 홀로 쓴 O와 ㅇ은 남았다 |
| KISA 상담 1,283건 | 정상 | '010-****-****', '02-1234-5678' 같은 가짜 번호. docx·PDF 파일 2개가 글로 읽혀 섞여 있었다 |
| 금감원 녹취 전사 706건 | 사기 | 음성에서 피해자 정보를 삐 소리로 가렸다. 사기범이 말한 이름과 번호는 실제 값이다 |
| 공식 사례 생성 사기 668건 | 사기 | 17%에 '000-00-0000', '공이 공공공' 같은 채움 값 |

그래서 정상 쪽에는 이름과 번호가 비어 있고 사기 쪽에만 실제 값이나 0 번호가 남았다. 앱이 실제로 채점하는 Whisper 전사에는 진짜 이름과 번호가 나온다.

**v3c에서 잰 영향** (같은 통화를 고쳐 쓰고 점수 비교, 분류기 단독)

- 통화 전체 판정에는 영향이 없었다.
  - 정상 99통의 가림을 실제 같은 값으로 바꿔도 오경보 0건.
  - 금감원 사기 125통의 숫자를 0으로 가려도 놓침 0건.
  - 생성 사기 43통의 0 번호를 실제 값으로 바꿔도 놓침 0건.
- 통화 첫 1–3마디에서는 가림이 만든 지름길이 보였다.
  - 정상 통화 첫마디에 '김민지 대리입니다'처럼 이름과 직함을 넣으면 80통 중 4통이 0.90을 넘었다. 사기 데이터에만 이름+직함 소개가 많이 남았기 때문이다(사기 31.8%, 정상 3.3%).
  - 사기 통화 둘째 마디에 피해자가 실제 번호를 말하는 문장을 넣으면 3마디 탐지가 74/80에서 63/80으로 줄었다. 같은 문장을 0으로 쓰면 75/80이었다.
- 학습 데이터 평가 몫의 정상 통화에서 가린 자리를 채우면 '한 번이라도 경고'가 3.6%에서 5.5%로 올랐다.

**다시 만든 데이터**

- 변환기에 `KEEP_MASK=1`을 더해 가린 자리의 위치를 그대로 남겼다(`convert_aihub_calls.py`, 지운 결과는 전과 똑같음을 확인).
- `mask_fill_batches.py`가 가린 자리에 번호를 붙인다. 찾는 대상은 세 가지다.
  - 기호 가림
  - AI Hub에서 한 글자로 가린 O·ㅇ
  - 0 번호, '공공공', 일부러 넣은 채움 값(홍길동, 1234, 5678 등)
- 대상은 3,710통화, 42,328곳이다.
- 채울 모델은 같은 40통화(314곳)로 Haiku와 Sonnet을 비교해 정했다.
  - 어느 모델인지 모르게 한 판정자가 찾은 오류는 Haiku 27건, Sonnet 6건이었다.
  - Haiku는 복창한 번호가 앞과 다르거나, 3자리 계좌번호처럼 말이 안 되는 값을 넣거나, 기관과 맞지 않는 은행을 넣었다.
  - 그래서 Sonnet으로 전체를 채웠다(묶음 134개, 약 1시간).
- `build_dataset_v5.py`가 값을 넣는다.
  - 42,272곳 중 42,261곳을 채웠고, 형식 검사를 통과하지 못한 11곳은 v3c 글로 뒀다.
  - KISA의 docx·PDF 2행은 뺐다.
  - 통화, 라벨, group, 나머지 글자는 v3c와 같다. 결과는 7,990건이다.
- 학습은 v3c와 같은 설정으로 했다(`klue/roberta-base`, `SPLIT=hash`, `PREFIX_AUG=3`, `NORMALIZE=1`, 같은 OVERSAMPLE, 3 epoch, 406초). 검증 정확도 99.63%, F1 99.02%.

## 2026-11-16 · 통화 분류기 v4 (Whisper 전사 말투 추가) — 교체하지 않음

앱은 Whisper가 무음 조각마다 받아 적은 글을 채점하는데, v3c는 사기 통화를 금감원 녹취의 기존 전사(KorCCVi)로 배웠다.
전사 말투가 정답의 단서가 되지 않게, 사기와 정상 양쪽에 같은 Whisper 전사본을 더해 다시 학습했다(한쪽에만 넣으면 v2 때처럼 '말투 = 사기'를 외운다).

- 데이터 `data/PhishCatch-Data-roberta_v4.json`, 9,650건(사기 1,632 / 정상 8,018):
  - v3c 데이터 7,992건 그대로
  - 사기 258건: 금감원 공개 녹취 327개(39.0시간)를 large-v3로 받아 적은 글. 기존 전사와 3글자 묶음 포함률 0.5 이상이면 그 통화 id를 group으로 써서 학습·평가가 갈라지지 않게 했고, 짝이 학습·평가 양쪽에 걸친 69개는 뺐다.
  - 정상 1,400건: AI Hub 민원(콜센터) 학습용 녹음을 받아 적은 글, 도메인마다 350건. 짝지어진 대본 대화의 group을 써서 v3c의 같은 대화와 같은 쪽에 둔다. 사기 핵심 신호가 든 통화는 뺐다(v3와 같은 규칙).
  - 발화는 단어 시각으로 앱과 같은 규칙(1.2초 넘게 쌓인 뒤 0.25초 쉬면, 또는 10초)으로 나눴다.
- 학습: v3c와 같은 설정(`klue/roberta-base`, `SPLIT=hash`, `PREFIX_AUG=3`, `NORMALIZE=1`, 같은 오버샘플링), 3 epoch, 516초. 검증 F1 98.51%.

## 2026-11-15 · 실시간 전사(음성 인식) 설정 비교

전사가 틀리면 분류기와 추적기도 틀리므로, 실제 녹음으로 지금 설정과 바꿀 수 있는 설정을 비교했다.

- 데이터: AI Hub 민원(콜센터) 녹음 32통(금융보험·다산콜센터, 46~145초) 중 정답 대본을 찾은 25통.
  대본은 파일 전체 전사와 3글자 겹침이 가장 큰 라벨 대화로 골랐다(평균 유사도 0.84, 0.3 미만은 제외).
- 지표: 글자 오류율(CER, 공백·문장부호 제외). 대본은 상담 각본이라 실제 발화와 조금 다를 수 있어 0%가 바닥은 아니다.
- 실시간 조각은 앱과 같은 방식으로 잘랐다: 최소 1.2초 쌓은 뒤 0.25초 조용하면 자르고, 10초면 강제로 자른다.
- 모델: faster-whisper large-v3 (fp16, H100). 코드: 서버 `~/voiceguard_tools/stt_bench.py`.

| 설정 | CER | 조각당 전사 시간 (평균 / p90) |
| --- | --- | --- |
| 파일 전체 전사 (녹음 파일 분석, 통화 종료 후 재전사) | 8.8% | - |
| **이전 실시간**: 무음 조각, beam 1 | 13.0% | 0.11초 / 0.14초 |
| **현재 실시간**: 무음 조각, beam 5 | **12.2%** | 0.13초 / 0.17초 |
| 고정 3초 조각, beam 1 (참고, 처음 4통) | 23.5% | 0.12초 |
| 무음 조각 + 앞 조각 문맥 / + 도메인 단어(hotwords) (처음 4통) | 14.1% / 14.7% | 0.15초 |
| 10초 창을 다시 전사해 새 단어만 붙이기 (단순 구현) | 28.8% | 0.33초 |

- 조각 단위 전사가 가장 큰 손해다(파일 전체 8.8% 대 실시간 12~13%). 그래서 통화가 끝나면 전체 녹음을 다시 전사하고
  상태도 다시 추적해 결과 화면·신고 요약·수사 화면은 정확한 전사로 바꾼다(이미 적용되어 있음).
- GPU에서는 실시간 조각도 beam 5로 바꿨다(오류 6% 감소, 지연 0.02초 증가). 앞 조각 문맥과 도메인 단어는 무음 조각에서
  효과가 없어 쓰지 않는다. 겹치는 창으로 다시 전사하는 방식은 제대로 하려면 두 번 연속 같은 글자만 확정하는 방식
  (whisper_streaming의 LocalAgreement)이 필요해 다음 과제로 둔다.

- 리턴제로가 공개한 벤치마크(업체가 직접 잼, 날짜 없음)에서 저음질 전화 CER은 RTZR 4.40, CLOVA 6.49, AWS 7.59, Azure 9.87,
  OpenAI Whisper API 17.27이었다. 방향만 참고한다. 출처: github.com/rtzr/Awesome-Korean-Speech-Recognition
- 권장: 지금 구조(자체 Whisper + 종료 후 재전사)를 유지하고, 시간이 되면 리턴제로 실시간을 같은 25통으로 A/B 시험한다.
  화자 구분이 필요하면 AWS Transcribe가 후보다. 출처 목록은 이 기록을 만든 세션의 조사 결과(업체 문서 링크)를 따른다:
  developers.rtzr.ai/docs/stt-streaming, docs.aws.amazon.com/transcribe, learn.microsoft.com/azure/ai-services/speech-service,
  api.ncloud-docs.com/docs/ai-application-service-clovaspeech-grpc.

### 왜 다시 학습했나

v2 기록의 한계에 "사기와 주제가 같은 정상 통화에서 분류기 점수가 자주 기준을 넘는다", "실제 정상 통화로 평가하지
못했다"가 있었다. AI Hub의 실제 콜센터 상담 데이터로 재 보니 문제가 생각보다 컸다.

- 분류기 단독: AI Hub 정상 상담 5,041건(Validation) 중 30.2%가 통화 중 한 번은 주의 기준을 넘었다. 은행 상담은 69.2%,
  증권 상담은 55.4%였다. "스마트폰으로 계좌이체를 하고 싶습니다 / 이용하시는 은행이 어디십니까?" 두 마디에 1.00이 나왔다.
- 실제 녹음: 민원(콜센터) 데이터의 녹음 32통을 Whisper로 받아 적어 채점하니 금융 상담 4통이 강한 경고(1.00)까지 갔다.
- 전체 시스템(분류기 + 상태 추적기): 분류기가 1.00을 준 정상 상담 14건을 회귀 평가처럼 흘려보내니 9건에 경고가 떴다.
  추적기도 상담원의 본인 확인("주민등록번호 말씀해 주세요")을 '정보 요구' 단계로 보고 위험도 0.7~0.98을 줬다.

Claude 추적기가 화면 위험도의 70%를 맡아도 막지 못했고, 추적기가 늦거나 실패하면 분류기 점수가 그대로 쓰이므로 둘 다 고쳐야 했다.

- **가림 표시 정리**: 금융분야 데이터는 숫자·이름을 '●', '▲', '△', 'O O O'로, 기관명을 'OO은행'으로 가렸다. 기존 학습
  데이터에는 '●'가 전혀 없고 'OO'는 생성한 사기 통화에만 조금 있어서, 그대로 넣으면 모델이 "가림 표시가 있으면 정상"을
  배운다. 'OO은행' 류는 레코드의 실제 기관명(예: 하나은행)으로 바꾸고, 나머지 가림 표시는 지웠다(지운 뒤 새로 드러나는
  가림까지 반복해서 정리, 남은 통화 0.2% 미만).
- **어려운 정상 사례 고르기**: 학습 분할 16,957건(분류별 최대 400건)을 v2 모델로 채점해, 통화 중 한 번이라도 0.5 이상이
  된 통화를 점수 높은 순으로 넣었다(출처마다 최대 1,500건). 말투·주제를 넓히려고 나머지에서 분류별로 고르게 700건씩 더 넣었다.
- **사기 핵심 신호가 든 상담은 뺐다 (826건)**: 원격 지원·제어, 앱 설치, 피싱·사기 언급, 검찰·경찰·금감원, 안전계좌·보호조치,
  명의도용이 나오는 상담이다. 진짜 상담이라도 정상으로 가르치면 모델이 그 신호 자체를 무시한다. 첫 후보(v3)가 실제로
  "카드 배송 + 원격지원 앱 설치" 사기 대본을 놓쳤다(증권사 HTS 원격 지원 상담 때문으로 보인다).
- **기존 정상 데이터 2배 반복**: 클래스 가중 손실은 정상 전체의 무게를 고정하므로, 정상을 3,900건 늘리면 KISA 상담·쌍둥이
  통화 같은 기존의 어려운 정상 사례 몫이 47%에서 19%로 줄어 그쪽 오경보가 늘었다(첫 후보 v3에서 KISA 4.2% → 10.0%).
  학습 때 기존 정상(KISA, 쌍둥이, 일반 통화, 생성 금융 통화)을 2배 넣어 되돌렸다 (`train_transformer.py`의 `OVERSAMPLE`).
- 코드: `build_dataset_v3.py`(데이터 구성), `eval_external.py`(외부 통화 채점), `eval_audio.py`(실제 음성 채점).

### 상태 추적기 기준 보정

분류기만 고쳐서는 부족했다. 추적기 스스로 정상 상담을 사기로 본 경우(위험도 0.9 이상 + 정보 요구·금전 요구 단계)는
단계 하한 규칙 때문에 분류기 점수와 상관없이 강한 경고가 된다. 프롬프트에 다음을 넣었다.

- 정상 절차: 고객이 먼저 문의한 업무를 처리하려고 성함·생년월일·주민등록번호·계좌번호를 묻는 것, 비밀번호·인증번호를
  상담원에게 말하지 않고 ARS·본인 앱에 직접 입력하게 하는 것, 본인 계좌 간 이체·공식 가상계좌 납부·환불 안내, 고객이
  자기 대출·보험료·대금을 그 기관에 내는 방법 안내. 이것만 있으면 단계 none, 위험도 0.2 이하.
- 그래도 사기 신호로 볼 것: 인증번호·비밀번호를 말로 불러 달라고 함, 상대가 알려준 링크·앱(원격제어 포함) 설치, 본인 명의가
  아닌 계좌·'안전계좌'로 이체, 현금 전달·상품권, 범죄 연루·명의도용·해킹을 이유로 한 긴급 조치, 기존 대출을 다른 계좌로
  먼저 갚으라는 요구, 대출·환급을 받으려면 먼저 수수료·보증금을 내라는 요구, 비밀 유지, 다른 번호로 전화하게 유도.
  (문자 속 번호로 전화한 가짜 고객센터를 놓치지 않기 위해서다.)
- 조정은 dev 14건(분류기가 1.00을 준 정상 상담, 출처마다 2건)으로만 했고, 처음 보는 test 28건으로 최종 확인했다.

### 공개 데이터 조사

- 이 과제(사기범이 처음부터 만든 가짜 공문 대 진짜 문서)에 맞는 공개 데이터셋은 한국어에도 외국어에도 없었다.
- AI Hub: '위조', '위변조' 검색 결과는 얼굴 위조 방지와 필체 모사 데이터뿐이다. 공공행정문서 OCR(약 90만 장)은
  정상 문서만 있어 정상 표본으로만 쓸 수 있고, 신청·승인이 필요하다.
- 공공데이터포털: 보이스피싱 통계, 영상, 설문만 있고 문서 이미지는 없다.

  SIDTD와 MIDV-2020은 유럽 모의 신분증이다.
- 그래서 경찰청, 금융감독원, 검찰, 언론이 "사기범이 만든 문서"라고 밝혀 공개한 이미지와, 발급 기관이 공개한

### 왜 다시 학습했나 (v1의 문제)

v1(KoELECTRA)은 학습 때 평가로는 정확도 99%였지만, 그 평가는 학습 데이터와 같은 종류의 통화만 봤다.
다른 종류의 통화로 재 보니 두 가지 문제가 있었다.

1. **모르는 유형을 못 잡는다.** 사기 데이터가 금감원 공개 녹취(기관 사칭, 대출 사기) 두 유형뿐이라
   납치 협박·지인 사칭·카드배송 사칭 대본에는 0~6%의 점수를 줬다.
2. **주제만 보고 사기로 본다.** 피싱 피해를 상담하는 정상 통화(KISA 118)의 약 60%에서 통화 중 한 번은
   주의 기준(0.70)을 넘었다.

중간 실험에서 배운 것: 정상 데이터만 늘리거나 통화 앞부분 증강만 넣으면 오히려 나빠진다. 사기 데이터가
한 출처(금감원 녹취 전사)뿐이면 모델이 내용이 아니라 "그 출처의 전사 말투"를 사기로 외운다. 사기 쪽
데이터의 유형과 출처를 함께 넓혀야 한다. (후보 `koelectra_prefix`, `koelectra_v2a`는 그래서 쓰지 않았다.)

### 공식 사례 기반 생성 방법

- **근거 자료**: 금융감독원 「보이스피싱 피해사례」 72건, 「소비자경보」 40건, 경찰청 통합대응단
  「피싱 예·경보」 2건, 「피싱 시나리오」 7건. 본문을 쓸 수 있는 121건만 썼다(경찰청 예·경보는 대부분
  이미지라 제외됨). 수집 결과는 서버 `data/official/cases.json`.
- **생성**: 사례 설명을 그대로 주고, 그 수법이 실제 통화에서 어떻게 들릴지를 Claude(Opus 5.5, Batch API)로
  전사본 형태로 만들었다. 사례 하나당 사기 통화 4개(끝까지 속는 통화, 의심하는 통화, 초중반에 끊기는 통화,
  확인하겠다는 것을 막는 통화)와 정상 쌍둥이 통화 3개.
- **정상 쌍둥이 통화를 넣은 이유**: 같은 주제(카드 배송, 대출 안내, 가족의 돈 부탁)가 정상적으로 일어나는
  통화를 함께 넣어야 모델이 "주제어 = 사기"로 배우지 않는다.
- **사용량**: 요청 288건, 입력 약 85만 토큰, 출력 약 77만 토큰.
- 코드: `backend/app/generate_official_scenarios.py`

### 한계

- 새 유형(지인 사칭, 카드배송, 기타)의 평가 통화도 Claude가 생성한 것이다. 학습에 쓰지 않은 사례에서
  만든 통화로 평가했지만 실제 통화보다 쉬울 수 있다. 실제 녹취로 확인한 것은 기관 사칭과 대출 사기뿐이다.
- 납치 협박은 공식 사례가 4건뿐이라 평가셋에 들어가지 않았다. 별도 대본 1개로만 확인했다.
- 사기와 주제가 같은 정상 통화에서 분류기 단독 점수가 통화 중 한 번이라도 기준을 넘는 비율이 24~43%다.
  화면의 위험도는 추적기 점수와 합쳐지므로 회귀 평가에서는 오경보가 없었다.
- 실제 전화 음질의 정상 통화로는 평가하지 못했다(공개된 정상 통화 녹취가 없음).

### 공식 사례 검색(RAG)을 탐지에 쓰지 않은 이유

금감원·경찰청 사례 121건을 검색 자료로 넣어 "지금 통화와 비슷한 공식 사례"를 찾는 실험을 했다(글자 n-gram TF-IDF).

| 색인 방식 | 결과 |
| --- | --- |
| 사례 설명문을 색인 | 생성 통화 668건의 원 사례를 1순위로 찾은 비율 37.9%, 3순위 안 57.3%, 유형 일치 65.0% |
| 사례에서 생성한 통화를 색인 (같은 사례는 빼고 평가) | 유형 일치 79.9% |

유형을 맞히는 정확도가 80% 수준이고 정상 통화와 사기 통화의 유사도 범위가 겹쳐서(0.14–0.24 대 0.23–0.40)

수사 지원 화면에 출처 링크가 달린 "유사 공식 사례"로만 붙인다. 이때 유형은 Claude 추적기가 정한 것을 우선한다.
