# 모델 구성

[README](../../README.md) · [보이스피싱 탐지 성능](detection.md) · [음성 인식·화자 분리 성능](transcription.md) · [학습 기록](../MODEL_TRAINING_LOG.md)

VoiceGuard가 쓰는 모델과 보관만 하는 모델을 한곳에 모았습니다. 모델마다 성능, 실행 위치, 쓰는 이유와 쓰지 않는 이유를 적습니다. 자세한 측정은 [음성 인식·화자 분리 성능](transcription.md), [보이스피싱 탐지 성능](detection.md), [학습 기록](../MODEL_TRAINING_LOG.md)에 있습니다.

## 전사 설정

전사는 통화 음성을 텍스트로 바꾸는 과정입니다. 실시간 음성 인식은 자체 운영 GPU 서버에서 처리하며, 리턴제로 기능을 활성화하면 해당 음성이 외부 API로 전송됩니다. 코드 기본값과 시연 서버 설정은 다음과 같이 다릅니다.

| 전사 | 코드 기본값 | 시연 서버 설정 (2026-11-16 기준) |
| --- | --- | --- |
| 통화 중 실시간 조각 (`STT_LIVE_ENGINE`) | 자체 서버의 Whisper large-v3 (`local`) | 자체 서버의 Whisper large-v3 (`local`) |
| 녹음 파일 분석 · 통화 후 재전사 (`STT_FILE_ENGINE`) | 자체 서버의 Whisper large-v3 (`local`) | 리턴제로 (`rtzr`) |
| 통화 중 전사 보정 및 화자 구분 (`STT_REFINE`) | 끔 (`off`) | 리턴제로 (`rtzr`) |

아래 '사용 중인 모델' 표는 시연 서버 설정 기준입니다.

### 통화 분류기 v5 성능

2026-11-16부터 서비스에 쓰는 v5를 이전 모델 v3c와 같은 평가로 비교했습니다.

| 평가 (분류기 단독, 기준 0.70) | v5 | v3c |
| --- | ---: | ---: |
| Whisper로 전사한 AI Hub 상담 녹음 1,400건 · 한 번이라도 경보 | **1.1%** | 2.0% |
| Whisper로 전사한 금감원 사기 녹취 258건 · 통화 끝 탐지<sup>1</sup> | **99.6%** | 97.7% |
| 비식별 구간을 채운 정상 통화(학습에 사용하지 않은 평가 분할) · 한 번이라도 경보 | **4.1%** | 5.5% |
| 피해자 실제 번호 문장을 넣은 사기 80통 · 3마디 탐지 (넣기 전 → 후) | **72 → 70** | 74 → 63 |
| v2 평가 분할 837통 · 사기 탐지율 (통화 끝 / 앞 3턴) | **99.7%** / 88.3% | 99.3% / **89.3%** |
| AI Hub Validation 정상 상담 5,041건(비식별 구간을 지운 글) · 한 번이라도 경보 | 0.9% | **0.7%** |
| 정상 상담 녹음 32통 · 경보가 난 통화 | 0통 | 0통 |
| 별도로 작성한 평가 시나리오 12개 | 11/12 (카드 배송 사칭 미탐지) | **12/12** |

<sub><sup>1</sup> 258건 중 212건은 같은 녹취를 다른 엔진으로 전사한 글이 학습 데이터에 있어, 처음 보는 사기 통화의 탐지율이 아니라 서비스와 같은 Whisper 전사에서도 사기를 잡는지 확인한 값입니다.</sub>

v3c는 정상 상담의 이름·번호 자리가 비어 있는 데이터로 학습해, 이름과 번호를 채운 정상 통화에서 오경보가 늘었습니다. v5는 비식별 처리 구간을 가상 정보로 채워 다시 학습한 모델이고, Whisper로 전사한 상담 녹음의 오경보를 2.0%에서 1.1%로 줄였습니다. 분류기만으로는 별도로 작성한 카드 배송 사칭 시나리오 하나를 놓칩니다. 화면 위험도의 70%는 Claude 상태 추적기가 정하며, 전체 시스템 결과는 [보이스피싱 탐지 성능](detection.md#전체-시스템)에 있습니다([학습 기록](../MODEL_TRAINING_LOG.md)).

추가 학습한 Whisper 세 모델에 공통된 원인은 학습 대본의 개인정보 마스킹 표기입니다. AI Hub 대본은 개인정보를 'ㅇㅇㅇ'로 가렸지만 녹음에서는 사람이 그 자리를 소리 내 읽었습니다. 그래서 모델이 소리 내 읽은 번호를 지우거나 대본 규칙대로 숫자를 적는 법을 익혔습니다([음성 인식·화자 분리 성능의 숫자 인식 한계](transcription.md#숫자-인식)).

## 학습 데이터의 비식별 처리 영향

공개 데이터는 개인정보를 비식별 처리해 배포하며, 처리 방식은 출처마다 다릅니다. 직접 학습한 모델 가운데 이 영향을 받는 것은 둘입니다.

- **Whisper 추가 학습:** 대본이 'ㅇㅇㅇ'로 가린 자리를 녹음에서는 소리 내 읽었습니다. 그래서 모델이 소리 내 읽은 번호를 지우는 법을 익혔습니다. 분류기의 사기 탐지는 유지됐지만, 번호로 다른 통화와 연결하는 수사 지원 기능에 쓸 수 없어 서비스에 쓰지 않습니다.
- **통화 분류기 v3c:** AI Hub 정상 상담 3,901건 중 87%는 이름·번호·주소 자리가 비어 있는 채로 학습됐습니다. 생성한 사기 통화에는 '000-00-0000' 같은 0 번호가 남았습니다.
  - 통화 끝 판정에는 영향이 없었습니다.
  - 통화 첫 1–3마디에서는 대화 의도보다 이름·번호 표기에 의존하는 편향이 확인됐습니다. 이름과 직함으로 소개하는 정상 통화가 잠깐 높게 나오고, 피해자가 실제 번호를 말하는 사기 통화는 초반 탐지가 늦어집니다.
  - 비식별 처리 구간을 Sonnet으로 채워 다시 학습한 v5는 두 번째 문제를 거의 없앴고, Whisper로 전사한 상담 녹음의 오경보도 2.0%에서 1.1%로 줄였습니다. 2026-11-16부터 v5를 씁니다. 이름+직함 소개에 반응하는 편향은 남았고, 분류기만으로는 별도로 작성한 카드 배송 사칭 시나리오 하나를 놓칩니다([학습 기록](../MODEL_TRAINING_LOG.md)).
- **문자 분류기:** 링크와 전화번호가 실제 값으로 들어 있어 다시 처리하지 않았습니다. 정상 문자 11%에 있는 '***'은 실제 알림 문자에서도 쓰는 이름 가림입니다.
- **영향 없는 것:** 기본 사전학습 Whisper, 리턴제로, Claude(직접 학습하지 않음), 화자 분리(음성만 봄).

평가 세트의 글도 비식별 처리를 따르므로, AI Hub 정상 상담 오경보(v3c 0.7%, v5 0.9%) 같은 수치는 실제 이름과 번호가 나오는 통화보다 좋게 나왔을 수 있습니다. 진짜 이름과 번호가 든 실제 정상 통화로는 아직 재지 않았습니다.

## 실행 위치와 외부 전송

- **자체 운영 서버:** 백엔드, Whisper large-v3, 분류기, 유사 사례 검색은 RunPod에서 빌려 직접 운영하는 GPU 서버에서 실행합니다. 공개 주소는 Cloudflare 터널로 이 서버에 연결됩니다. 학습과 대부분의 평가는 H100 서버에서 했습니다.
- **GPU가 필요한 것:** Whisper large-v3뿐입니다.
- **CPU로 실행할 수 있는 것:** 통화 분류기, 문자 분류기, 유사 사례 검색, 규칙, 로컬 화자 분리(앱 미연결)입니다.
  - 노트북 CPU에서 통화 분류기는 조각 하나에 0.5–2초가 걸려, 동시 통화가 많으면 처리가 밀립니다.
- **리턴제로 API로 보내는 것 (음성, 리턴제로를 켰을 때만):** 통화 중 전사 보정, 통화 후 재전사, 녹음 파일 분석입니다. 코드 기본값에서는 보내지 않고, 시연 서버는 세 가지 모두 켜 두었습니다.
- **Anthropic API로 보내는 것 (글, 문자 캡처, 문서 사진):** 상태 추적기, 대응 에이전트, 문자 검사 보조, 문서 점검, 사건 개요, 신종 수법 카드 초안, 탐지 근거 설명입니다.
